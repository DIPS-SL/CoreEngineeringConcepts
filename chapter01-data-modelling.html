Partitioning vs Sharding Key Distinction
Partitioning splits data within one server. Sharding distributes data across multiple machines.
🔀 Three Partitioning Strategies
Strategy Split by Lives on Our use case
Horizontal Rows by range or hash One server (partitioning) or many servers (sharding) Posts & Follows tables
Vertical Columns — hot vs cold Same server, different tables User profile vs auth data
Functional Entire data domains Separate servers per service User DB / Post DB / Graph DB
🔑
Partitioning lives on one server. Sharding spans many.
Partitioning is a logical split — data stays on one machine, organised differently. Sharding takes it further: each partition lives on a separate physical server. That is what makes sharding a true scale-out strategy, not just an organisational one.
🎙
Key Takeaways
What every engineer should know about data modeling at scale.
🗄
Single DB first
For small scale, a single SQL database is perfect. Simple JOINs, zero overhead, fast queries. Don't over-engineer early.
🔀
Sharding
Horizontal partitioning across servers. user_id % N routes each request to the right shard. No single node is a bottleneck.
📐
Partitioning
Three strategies: horizontal (rows), vertical (columns), functional (domain). Sharding is horizontal partitioning at server level.
🧩
Microservices
Social Graph Service owns relationships. Post Service owns content. Each deploys and scales independently.
💡
The rule of thumb
Start simple. Scale when you feel the pain. Premature sharding adds operational cost with zero benefit. The same query that takes 3ms at 30 users takes 8 seconds at 100M — that's your signal to shard.
