Infinite Scroll & Cursor Pagination
How does Facebook let you scroll through years of posts without the app slowing to a crawl? The answer changed how every major feed on the internet is built.
📄
The Page Number Illusion
OFFSET seems simple. But at page 5,000 the database must scan and discard 100,000 rows just to return 20.
🌊
Infinite Scroll Changed Everything
Nobody clicks "page 57". Infinite scroll asks what comes next — a fundamentally different question.
📉
The Drift Bug
A new post inserts while you scroll. OFFSET shifts every row — you see duplicates or miss posts entirely.
⚡
O(1) vs O(n) at Depth
Cursor pagination costs the same at page 1 or page 5,000. OFFSET cost grows linearly with depth.
📘
Real-world inspiration · Facebook, Instagram, Twitter
Every major social feed — Facebook's News Feed, Instagram's Home Feed, Twitter's Timeline — switched from offset to cursor pagination early in their scaling journey. At hundreds of millions of users, a single deep-page OFFSET query was taking seconds and hammering the database on every scroll event.

The Naive Facebook Feed 100 Users
Facebook launches. A hundred users. A few hundred posts. Pagination is simple — and it works.
What is pagination? Your database has millions of rows. You can't send them all at once. Pagination means: give me rows N through N+20 — one chunk at a time.
📄 The query — page 1 of the feed
-- Get the first 20 posts for the News Feed SELECT post_id, content, author, created_at FROM posts ORDER BY created_at DESC -- newest first LIMIT 20 -- return 20 posts OFFSET 0; -- start from the beginning (page 1)
🧠 How OFFSET works — the formula
OFFSET = (page number − 1) × page size
Page 1 → OFFSET 0  ·  Page 2 → OFFSET 20  ·  Page 3 → OFFSET 40  ·  Page 100 → OFFSET 1,980

Facebook Grows 100M Users
Same query. Same SQL. Now the posts table has billions of rows — and the user keeps scrolling.
📄 Deep in the feed — page 5,000
-- User has scrolled to page 5,000 of their feed SELECT post_id, content, author, created_at FROM posts -- 5 billion rows now ORDER BY created_at DESC LIMIT 20 OFFSET 99980; -- skip 99,980 rows first ← problem
Why is this slow? OFFSET does not jump. The database engine reads rows 1, 2, 3 … 99,980 sequentially, throws each one away, then returns rows 99,981–100,000. Every deep page is a full sequential scan from the beginning.

The Feed Keeps Changing The Real Problem
Performance was fixable. This is worse — OFFSET pagination gives you wrong results on a live feed.
The hidden assumption: OFFSET pagination assumes your data never changes between requests. Facebook's feed changes every second — this assumption is always wrong.

Why Post D duplicated
Page 1 loaded OFFSET 0–3 (posts A, B, C, D). New post inserted. Page 2 loads OFFSET 4 — but now offset 4 points to Post D again, shifted down by the insert.
What about skipped posts?
If a post is deleted instead of inserted, the opposite happens — rows shift up, and a post between page 1 and page 2 silently disappears. The user never sees it.
⚠
This is the real reason cursor pagination exists
Not performance. Consistency. OFFSET counts rows from the start each time. On a live feed that changes every second, that count is always stale. Cursor pagination bookmarks by value — new inserts can't shift it.
🎙
Cursor Pagination — The Fix Solution
Instead of counting rows from the top, bookmark your position by value. The database jumps directly there.
🗄 Step 1 — A simple posts schema
📝 posts
id PK · auto-increment
user_id FK → users
content text
created_at INDEX ← cursor column
The cursor column must be: monotonic (always increasing), indexed (fast seek), and ideally unique. created_at or id are the classic choices.
🔀 Step 2 — OFFSET vs Cursor, side by side
❌ OFFSET approach
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20
OFFSET 99980;
-- scans 99,980 rows first
✓ Cursor approach
SELECT * FROM posts
WHERE created_at <
  '2024-03-15T14:22:09Z'
ORDER BY created_at DESC
LIMIT 20;
-- index seek · constant time
📡 Step 3 — The API returns a cursor token with every response
{ "posts": [ { "id": 8821, "content": "Just shipped…", "created_at": "2024-03-15T14:25:00Z" }, { "id": 8820, "content": "Hot take…", "created_at": "2024-03-15T14:22:09Z" } ], "nextCursor": "2024-03-15T14:22:09Z" // ← timestamp of last post }
Next request: GET /feed?cursor=2024-03-15T14:22:09Z
The server runs: WHERE created_at < '2024-03-15T14:22:09Z' — index seek, instant.

Both methods return the same 20 posts. But how they get there is completely different.

1. Read row 1 → discard

3. Read row 3 → discard

1. Look up cursor value in index
2. Index points directly to position
3. Read row N → keep
4. Read row N+1 → keep
···
20. Read row N+19 → keep

Total: exactly 20 rows touched

Key Takeaways — Pagination in Production
Two strategies. Different tradeoffs. One clear winner for live feeds at scale.
📄
OFFSET Pagination
Works perfectly at small scale and for static data. Simple to implement. Breaks at depth with live data: O(n) scan cost, row drift on concurrent writes, silent duplicates and skips.
🔖
Cursor Pagination
O(1) per page regardless of depth. Immune to drift — inserts and deletes can't shift the cursor. Requires a monotonic indexed column. Forward-only — no random page access.
🌊
Infinite Scroll Pattern
Each API response returns a nextCursor token. On scroll trigger, client sends the token back. Server issues a WHERE seek. The user never sees a page number.
🏭
Industry Adoption
Facebook News Feed, Instagram Home Feed, Twitter/X Timeline, LinkedIn Feed — all use cursor-based approaches. OFFSET is reserved for admin dashboards and internal tools.

The rule of thumb
Use OFFSET for admin dashboards, reports, and internal tools where data is static and page-jumping matters. Use cursor pagination for any user-facing infinite scroll on live data. The moment users can concurrently write to your feed, OFFSET becomes a bug factory — not just a performance problem.
