Races Hide at Low Scale
A read-modify-write bug is invisible with one user clicking at a time. It only shows up when hundreds do it in the same millisecond.
🔒
Locks Kill Throughput
Row locks make writes correct but serial. Under a thundering herd, thousands of requests queue up waiting for one row.
⚛️
Atomic Ops Win
A single atomic instruction — like Redis INCR — has no gap between read and write. There is no race to lose.
🌊
Eventual Consistency Is Fine
Nobody notices if a like count is 2 seconds stale. Relaxing consistency where correctness allows it buys enormous scale.
🧵
The Core Insight
The fix for a concurrency bug is rarely "add a lock." It's redesigning the operation to be atomic, and relaxing consistency guarantees exactly where the domain allows — which for a like counter, is almost everywhere.

Fix 2 — Write-Behind Batching Solution
Redis holds the hot, exact count. A background worker flushes it to the database on a timer — not on every click.
🪣 Write-behind flow — 50,000 likes → 1 DB write
Flush interval DB writes/day (viral post) Staleness window Trade-off
Every write (naive) ~4.3M writes 0s (but races) Correctness risk
Every 5 seconds ~17k writes ≤5s Sweet spot for likes
Every 60 seconds ~1.4k writes ≤60s Too stale for live UI
🪣
99.6% fewer database writes
A viral post generating 50,000 likes/minute produces one database write every 5 seconds instead of 50,000. Redis is the source of truth for the live count; the database is a periodically-synced backup. If Redis restarts, worst case you lose a few seconds of increments — acceptable for a like counter, unacceptable for a bank balance.

The key insight: match the tool to the contention
Row locks are correct but serialize a hot row into a queue — fine at low contention, catastrophic on a viral post. Optimistic locking retries under contention and can thrash. Atomic operations sidestep the problem entirely: there is no lock to wait for and no version to conflict, because there was never a gap to race in.

Key Takeaways
What every engineer must know about counters and concurrency.
🫥
Race Condition
Read-modify-write has a gap between reading a value and writing it back. Two concurrent writers can both read the same value and one update silently disappears.
⚛️
Atomic Operations
INCR, compare-and-swap, and other single-instruction ops leave no gap to race in. This is almost always cheaper and simpler than adding a lock.
🌊
Thundering Herd
A viral post turns one database row into a bottleneck as thousands of requests queue for the same lock at once. Design for the spike, not the average.
🪣
Eventual Consistency
Write-behind batching lets an in-memory counter absorb load and flush to durable storage on a timer. Perfect for approximate counters — wrong for anything that must never be stale.
💡
The rule of thumb
Don't reach for a lock first. Ask whether the operation can be made atomic, and whether the read path can tolerate staleness. A like counter needs neither strict serialization nor real-time accuracy — which is exactly why an atomic Redis counter with a periodic flush beats a row lock at every scale that matters.
