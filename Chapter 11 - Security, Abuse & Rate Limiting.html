Rate Limiting Algorithms Deep Dive
Token bucket isn't the only option. Every engineer should know these four trade-offs.
AlgorithmHow it worksBurst handlingTrade-off
Fixed Window Count resets every N seconds Poor — edge bursts Simple, but 2x traffic at window boundary
Sliding Window Weighted count across overlapping windows Good Smoother, more memory per client
Token Bucket Tokens refill at fixed rate, consumed per request Allows short bursts up to capacity Our choice — simple, burst-friendly, low memory
Leaky Bucket Requests queue, processed at constant rate None — smooths everything Predictable output, adds queueing latency
🪣
Why token bucket wins for APIs
It tolerates natural bursts (a user opening five tabs at once) while still capping sustained abuse — the best fit when fairness matters more than perfectly smooth throughput.
🎙
Key Takeaways
What every engineer must know about security, abuse, and rate limiting.
🪣
Token Bucket
Refill tokens at a fixed rate, consume one per request. Bursts are absorbed; sustained abuse is capped. Applied per-user, per-IP, or per-endpoint.
🔑
JWT & OAuth
Short-lived signed access tokens plus a longer-lived refresh token. A stolen access token expires fast; the refresh flow can be revoked.
🧱
Layered Limits
Rate limit at the IP layer, the account layer, and the endpoint layer separately — one bad actor shouldn't be able to starve everyone else.
🤖
Spam ML Pipeline
Feature extraction + classifier score every post in milliseconds. Low-confidence cases route to human review instead of an outright block.
💡
The rule of thumb
Authentication proves who someone is. Rate limiting bounds what they can do. Abuse detection catches what slips through both. You need all three — none of them alone is enough at scale.
